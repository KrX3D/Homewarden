# Homewarden - project notes

Self-hosted Docker app for a homelab: knows which devices are on, what software
versions they run, what needs updating, and updates individual parts or everything.
Combines what Uptime Kuma (presence), PatchMon (patch status), WUD (image updates),
Komodo (Docker management), Beszel (resource stats), Scrutiny (SMART) and NetAlertX
(network discovery) do, in one tool configured entirely through the GUI.

This file is the working memory for AI agents and contributors. Keep it current: when a
decision is made or changed, update it in the same PR.

## Origin

- Owner: KrX3D. Homelab: Unraid (Docker host, also runs this app), Proxmox with LXCs,
  Raspberry Pis (OctoPi printers, AdGuard Pi), Proxmox Backup Server as an Unraid docker
  that only runs a few hours, UniFi network, Windows machines managed by DeployDeck.
- Several devices are only on sometimes (OctoPi only while printing, PBS a few hours).
- Ansible was tried before and dropped: it needed code/YAML for everything, had no
  state or UI, and setup was hard to figure out. Homewarden must never require writing
  config code. Old playbooks (inactive): `\\192.168.90.114\Scripts\Ansible`.

## Stack

- Go backend, React frontend (Vite) embedded into the binary, one image. Same stack as
  DeployDeck so DeployDeck can later become the Windows integration.
- SQLite via the pure-Go driver `modernc.org/sqlite` (no CGO, easy cross-compiling),
  WAL mode. One file under `/data`, so backing up Homewarden = copying appdata.
- Light and dark mode required, follows the system with a manual override.
- Image: `ghcr.io/krx3d/homewarden`, built by GitHub Actions for linux/amd64 and
  linux/arm64. `latest` + `0.1.<commit count>` on main, semver tags on `v*` tags.
- Optional agent: same repo under `/agent` later, cross-compiled for Pi (ARM), x86 and
  Windows.

## Decisions

### Presence

- Staged, not on/off: Offline -> Reachable (ping/TCP answers, may still be booting)
  -> Ready (real service answers: SSH login works or the API responds, and stays so for
  a settle time, default 60 s, per device) -> scan.
- A scan only starts at Ready. Failed scans retry with backoff.
- Offline devices show "last seen X".

### Connection

- Per device: agentless (SSH, WinRM, native API) or agent, switchable later.
- SSH keys are generated by the app; the user never handles them.
- Least privilege where possible (e.g. sudo rule for apt only instead of full root).
- Secrets encrypted at rest with a master key.
- Integration setup (Integrations, Set up; also from the device's Integration card):
  shared settings and an SSH connection per integration, stored as setting
  `integration.defaults.<id>` ({settings, connection}). Lookup order for a setting:
  device value, then integration default, then manifest default. Empty strings/null
  count as unset, so the device card saves only fields the user filled. A device
  without its own credential (and not on the agent) uses the shared connection as a
  whole (credential, user, port, sudo). The merge (`store.WithDefaults`) happens at
  read time in `Host.Call`, `conn.Target` and the backup/restore jobs; never save its
  result. Devices set up before this still carry the manifest defaults the old card
  saved; those win until cleared. Credentials used by a setup count in "used by".
- Manifest setting `scope: "device"` marks values that differ per device (OctoPrint
  url, Proxmox node, Docker endpoint, Windows hostKey/showShare). They only appear in
  the device's Integration card; all other settings live in the setup page and appear
  on the device only inside a collapsed "override" section. The setup page shows the
  manifest howto (open until something is set up); credential settings carry a help
  text saying where the key comes from. Howtos refer to the setup page, not the device.
- Howto text is rendered structured (`Howto` in integrationSetup.tsx): "1." lines are
  numbered lists, "- " bullets, short lines ending in ":" headings. Write guides that way.
- Setting `credentialUsername` (Text) labels the user name of a token credential when the
  API needs one (Proxmox/PBS token id). Without it, the New credential dialog opened from
  that setting does not ask for a user name for tokens.
- Credentials can be created inline: Connection card and integration setup open the
  vault's `CredentialModal` (export, `types` limits the kinds).

### Updates

- Detection: current version, available version, per component (e.g. OctoPrint core,
  each plugin, OctoPi OS separately).
- Per device/component policy: manual, scheduled, auto, or external trigger (API/MQTT).
  The user decides; the UI warns about consequences ("this restarts the host").
- Busy guards, both kinds, all configurable:
  - built into integrations (OctoPrint: block while a started print job is active,
    including its preheat phase; plain manual heating does not block)
  - generic rules built in the GUI (e.g. container CPU above N%, API returns X).
  - Guard mode per device: block, warn, or ignore. Default for generic: off.
- Optional backup-before-update per device.
- Rollback to a pickable previous tag (Docker) or the pre-update backup/snapshot.
- Changelog shown before updating, "reboot required" flag, EOL OS detection,
  security-flagged updates highlighted.
- Homewarden's own host and Homewarden itself: notify only. A container cannot cleanly
  replace itself, and recreating it outside Unraid's template desyncs the Docker tab.
- Packages inside container images (e.g. nano): shown as info/CVE list only, since
  in-container updates are lost on recreate. For own images (GitHub or local Gitea):
  either open a PR that bumps the base image/package so CI builds a new image, or show
  exact step-by-step instructions. Never push directly.

### Backups

- Separate Backups section: targets (SMB share first), retention, per-device jobs.
- Backup health: last backup age per device, alert when older than N days, PBS results.

### Discovery and onboarding

- Auto-discovery (containers from Unraid/Docker, LXCs/VMs from Proxmox, UniFi client
  list, optional network scan) plus manual adding.
- Discovered devices land in an inbox: Add (then configure) or Ignore. Ignored devices
  are hidden in a list and can be re-added later.
- Home Assistant integration (REST, long-lived token, no SSH): components are HA's own
  `update.*` entities (Core/Supervisor = app, OS = os, add-ons by entity_picture
  `/api/hassio/addons/`, everything else plugin). Install via `update.install` (with
  `backup: true` where supported_features has 8), then poll the entity because the
  REST call returns early and Core/OS restart HA. Order: add-ons/others, Supervisor,
  Core, OS. Busy: any entity in_progress or `sensor.backup_backup_manager_state` not idle.
  Release notes: release_summary, GitHub release body when release_url is a GitHub tag.
- Integrations page: installed ones are not listed under Available (uninstalling brings
  them back); a newer catalog version shows as a pill + Update button on the installed card.
- The job list is the Activity page (`/activity`, web/src/features/activity.tsx; `/jobs/*`
  redirects there, notification links use /activity). Running jobs on top with live last
  log line, history grouped by day, filters (status, kind, device, search), paging with
  `GET /api/jobs?before=<id>&limit=`. A failed job stores `result.error` (runner), shown
  in the list. Script errors lose the JS "Error: "/"GoError: " prefix (`scriptErr`).
- Proxmox token privileges (Privilege Separation on): Sys.Audit, Sys.Modify (GET
  apt/update needs it; PVEAuditor is not enough), VM.Audit, Datastore.Audit, VM.Snapshot.
  A 403 names the missing one and both ways to fix it (`missingPrivilege` in main.js).
- One integration per device = what the device is and what gets updated on it.
  Information about a device from elsewhere is not a second integration: discover
  entries may carry `network` (stored in table `network_info`, one row per reporting
  device, shown in the Network card) and `enrichOnly` (never creates devices, only
  enriches matches by MAC/IP). UniFi reports every client this way (switch port or AP,
  SSID, signal, VLAN, uptime) on each scan of the console; `importClients` only decides
  whether unknown clients also land in the inbox. A discovered entry matching the
  parent itself (the UDM in its own device list) is skipped.
- UniFi `call()` turns connection errors into a hint that UniFi belongs on the console
  (users picked it on other devices to get network info).
- Network scan renames known devices whose name looks generated (container id, IP)
  when it finds a better one (fixes entries from before LooksGenerated existed).
- Inbox "Add" has an "as" select: picks the integration and takes over its presence
  config (`applyPresence` on PUT `/api/devices/{id}/integration`).
- Network scan: several ranges per scan (max 1024 addresses each, 4096 total, stored
  comma-separated in setting `discovery.cidr`). The result lists every address that
  answered with status new/inbox/known/ignored; the last result is kept in memory and
  returned by GET `/api/discovery` so the dialog shows it again. Scan button is always
  in the Devices header.
- Onboarding: guided how-to with exact steps per integration, test-connection buttons.
- Optional provisioning per integration (e.g. OctoPrint: restore last backup and
  reinstall plugins). Many integrations will not have it.

### Integrations ("marketplace")

- Core: devices, presence, vault, scheduler, jobs/history, backups, API/MQTT, UI.
- Integrations live in this repo under `integrations/<id>/`, with
  `integrations/index.json` as the catalog that the marketplace shows.
- An integration = manifest (name, icon, version, min core version, settings schema
  the GUI renders as a form, how-to text) + JavaScript run in an embedded sandboxed
  engine (no compiling, no new image per integration).
- Sandbox: a script only gets what the core grants (run a command on this device over
  SSH, call this device's API). This is the supply-chain protection.
- Catalog sources are a setting: GitHub by default, local Gitea can be added.
- Installed integrations are stored in `/data/integrations/<id>/<version>/` and loaded
  from there on every start. Never re-downloaded on boot; updated only when the user
  clicks update, pinned to an exact version, with a diff shown first.
- Built-in copies ship in the image as seed/fallback for offline first start.

### Monitoring extras

- Uptime Kuma monitor types (HTTP keyword/JSON, TCP, ping, DNS, Docker, push,
  MQTT, databases, gRPC), response-time graphs, cert expiry, status pages, maintenance
  windows, groups.
- Komodo/Beszel-style host and container stats (CPU, RAM, disk, network, temps) with
  history; its own section per device.
- SMART disk health (Unraid array, Pi SD cards), disk space warnings.
- New-device-on-network alerts (UniFi client list / scan).
- Docker hygiene: unused images/volumes with cleanup.
- Version history per device, kept 1 year.

### Auth

- LAN only, behind nginx. Never exposed to the internet, no VPN.
- First start: setup wizard creates the first admin (username chosen there). The
  wizard requires a one-time setup token printed in the container log, so nobody else
  on the LAN can claim the instance first.
- Local users, optional TOTP 2FA. OIDC SSO later (one implementation covers Authentik
  and Authelia).
- Roles: built-in Admin, Operator, Viewer plus custom roles with per-permission
  checkboxes, optionally limited to device groups.

### UI

- Device view default: card grid (A), switchable to fleet table (B) and host tree (C)
  via small icons top right. Remembered per user. An "Overview" summary page (counts,
  needs attention, recent jobs) may come later.
- Icon: "Pulse house" variant 6 "Chimney" (house with chimney and a heartbeat line).
  `assets/mark.svg` is the line mark (currentColor), `assets/icon.svg`/`icon.png` the
  app icon (white mark on accent #2f56c9, rounded square). Unraid template points at
  the raw `assets/icon.png` on main.
- Every `Modal` has a close X in its title bar; edit dialogs also have Cancel.
- Monitors page suggests one monitor per active device without one (frontend only,
  `suggestFor` in monitors.tsx): known web UIs (HA, OctoPrint, Proxmox, PBS, UniFi,
  DeployDeck) get HTTP, else the device's tcp ready port, else ping. Online devices are
  preselected; hidden suggestions are a per-browser convenience in localStorage.
- `Modal`: fixed title, own-scrolling body (`min-width: 0`, so wide `pre`/tables stay
  inside), footer always visible. `wide` for scripts, changelogs, scan results.

### Container

- Runs as PUID:PGID, default 99:100 (Unraid nobody:users). Nothing needs root:
  ping works unprivileged in Docker, the Docker socket only needs its group. The
  entrypoint (`docker/entrypoint.sh`) creates the user, adds it to the socket's group,
  chowns `/data` if needed, then drops privileges with su-exec. PUID=0 = run as root.
- Unraid template: `unraid/homewarden.xml`.

## Layout

- `cmd/homewarden/` - entry point: opens vault + DB, logs the setup token, serves HTTP
- `internal/store/` - SQLite (modernc, pure Go), migrations in `migrations.go`
  (append only; `PRAGMA user_version` counts them), one connection
- `internal/vault/` - AES-256-GCM for secrets; key from `HOMEWARDEN_MASTER_KEY` or
  `/data/master.key`
- `internal/auth/` - bcrypt passwords (min 10 chars), session tokens (stored as
  SHA-256), TOTP (RFC 6238), setup token, login rate limiter, permission catalog
- `internal/api/` - HTTP API. Every non-GET `/api/` request needs the `X-Homewarden`
  header (CSRF). Errors are `{"error": "<code>"}`; the UI translates `error.<code>`.
  `Server.Authed(perm, h)` and `Server.Handle` let other packages add routes.
- `internal/presence/` - probes (unprivileged ICMP via x/net/icmp "udp4", TCP, HTTP
  <500 = up) and the engine. `Next()` is the pure state machine (unit tested):
  2 missed reach checks = offline; ready needs the ready probe to pass for
  `settleSeconds`. `OnReady` callbacks fire on the transition to ready (scans hook in
  there). History in `presence_events`, pruned after 1 year.
- `internal/discovery/` - ping/port sweep of one or more CIDRs into the inbox
  (`status=discovered`, `source=scan`, `external_id=ip`).
- `internal/events/` - SSE broker at `/api/events` (`device.state`, `device.seen`,
  `device.changed`, `discovery.*`). Web hook: `web/src/useEvents.ts`.
- Devices: `status` active|discovered|ignored; `parent_id` builds the host tree;
  `presence` JSON {reach, ready, settleSeconds, intervalSeconds}; reach `none` = state
  comes from elsewhere (e.g. container state from its host integration).
- `web/src/extensions.ts` - `deviceSections` (cards on the device page) and
  `settingsTabs`; feature modules in `web/src/features/` push into them and are
  imported once from `main.tsx`.
- `internal/store/credentials.go` + `internal/api/credentials_handlers.go` - vault of
  ssh_key / password / token. Secrets are vault-encrypted, never returned by the API.
  SSH keys are ed25519 generated in-app (or a pasted unencrypted key). A credential
  referenced by any device config field ending in `credentialId` cannot be deleted.
- `internal/sshx/` - SSH dial/run, key generation, TOFU host-key pinning
  (`known_hosts` table keyed by host:port; mismatch = `host_key_changed`, the UI offers
  "trust the new key" which deletes the pin).
- `internal/conn/` - device `config.connection` {method: ssh, port, credentialId,
  user, sudo}. `Exec(..., privileged)` wraps in `sudo -n sh -c` when sudo is on.
  `InstallKey` logs in once with a password (never stored) and appends the public key.
- `integrations/` (repo root) - the catalog: `index.json` + one folder per
  integration. Also a Go package embedding everything as the built-in source. Bump the
  manifest `version` AND the index entry on every change. Remote sources fetch
  `<source>/index.json`, then `<source>/<path>/manifest.json` and its `files`.
- `internal/integrations/` - manifest parsing, registry (install = copy to
  `/data/integrations/<id>/<version>/`, row in `integrations` table; loaded from disk on
  start, never re-downloaded), and the goja sandbox (`Host.Call`).
- `internal/jobs/` - runner (4 workers, one job per device at a time, live log via
  `job.log`/`job.status` SSE) and `Software` (scan/update handlers, discovery of child
  devices, auto-scan on presence ready + every 6h, history/job pruning after 1 year).

Integrations at 0.9.x are beta: written from documentation and tested only against
fakes (proxmox, proxmox-backup, unraid). Bump to 1.0.0 once confirmed on real systems.
- Proxmox VE: reads via API (`PVEAPIToken=<tokenid>=<secret>`), installs via SSH
  (`apt-get`, LXCs with `pct exec`), snapshots LXCs before updating (keeps newest 3
  `homewarden-*`).
- PBS: API (`PBSAPIToken=<tokenid>:<secret>`, colon!), datastore usage, newest backup,
  failed tasks; package updates optional (off for PBS in Docker).
- UniFi: classic API (/proxy/network on UniFi OS), X-API-KEY or local login (TOKEN cookie + X-CSRF-Token); firmware via `cmd/devmgr upgrade`, gateways last.
- DeployDeck: session login (`POST /api/login`, cookie `dd_session`), reads `/api/hosts`
  + `/api/scripts`; update = `POST /api/scripts/{id}/run` (share) or
  `/api/scripts/{installScriptId}/install {computer}` (PC). Tested on a fake only.
- Windows: PowerShell through the agent (UTF-8 forced by the agent). Windows Update via
  the COM API (verified read-only on a real Windows 10 PC), winget table parsed by
  header positions (untested on real output; winget as SYSTEM found under WindowsApps).
- Windows + update scripts (DeployDeck replacement): optional `scriptsPath` (UNC to
  InstallationScripts). Detect reads `<scripts>\Log\State\*.json` and the PC key the
  scripts use (`GetPcByUUID.ps1`, else hardware UUID; logged with its source) and lists
  `ps:<Script>` where installedByHost[key] < share version; `showShare` adds
  `share:<Script>` (share behind vendor). Update runs the script on the PC through the
  agent and logs its `##deploydeck:` line. Share login is sent on stdin. Verified
  read-only against the real share from a real PC. Not replaced: script editing via
  Gitea PRs, code signing, container-side (pwsh on Linux) runs.
- Agent on Windows strips PSModulePath before starting powershell.exe (PS 7's path breaks
  5.1 built-in modules).
- Unraid: SSH as root; plugins via `/usr/local/sbin/plugin check|update <file>.plg`;
  OS is notify-only (`warning: self`); busy during parity check/rebuild and mover.
- `ssh.exec` with `sudo: true` adds no sudo when the SSH user is root. The sudo prefix
  only covers the first command of a compound shell line, so scripts that may run as
  non-root must keep privileged calls to single commands.

### Agent

- `cmd/homewarden-agent` (stdlib only) long-polls `POST /api/agent/poll` with
  `Authorization: Agent hwa_...`, runs commands with `/bin/sh -c` (Windows:
  PowerShell), posts `/api/agent/result`. Enrollment: device Connection card creates a
  one-time token (24 h); `/agent/install.sh` / `install.ps1` download the binary from
  `/agent/download/<os>-<arch>` (built into the image under
  `/usr/local/share/homewarden/agent`) and run `-enroll-only`, then install a systemd
  service / Unraid `/boot/config/go` line / Windows scheduled task as SYSTEM.
- Devices with `config.connection.method = agent` route `ssh.exec`, guards and
  connection tests through `internal/agent.Hub`; presence reach method `agent` = polled
  within 75 s. `/api/agent/*` is exempt from the CSRF header (header auth).

### Integration contract (main.js)

Plain ES5-ish JS (goja), synchronous. Functions, each `(ctx, arg)`:
- `detect(ctx)` -> `{facts: {...}, components: [{id, name, group, installed,
  available, updateAvailable?, security?, updatable?, meta?}]}`. `group`: os, package,
  container, image, app, plugin, action. `meta.warning`: reboots | restarts-services |
  restarts-host | restarts-container | self (UI shows a pill). `meta.changelog`: URL.
  `updatable:false` = notify only.
- `update(ctx, ids)` - ids are component ids, or `["*"]` for everything. Throw on
  failure. The core rescans afterwards and writes version history itself.
- `busy(ctx)` (capability `busy`) -> `{busy, reason}`; blocks updates unless forced.
- `restore(ctx)` (capability `restore`) -> `{upload: {url, field, headers}}`; the core
  uploads a stored backup there as multipart with an exact Content-Length (restore job,
  `POST /api/backups/{id}/restore {deviceId}`: onto the same or a replacement device).
- Manifest `sudoers` ($USER placeholder): Install key can add it with the one-time
  password (`sudo -S`, checked with visudo) so a fresh device needs no terminal.
- `changelog(ctx, componentId)` (capability `changelog`) -> `{text, url}`, shown in a
  modal (`GET /api/devices/{id}/changelog?component=`).
- `choices(ctx, componentId)` (capability `choose`) -> `{current, choices[{value, label,
  note}]}`; picking one runs an update of `"<componentId>@<value>"` (Docker: switch or
  roll back the tag).
- Manifest `ports`: [{target device|internet|homewarden, proto, port, note}] shown in
  the Integration card and Settings, Network (keep in sync with README "Network and
  firewall").
- Discovered devices are merged into an existing device with the same MAC or address
  (`mergeDiscovered`): MAC filled in, name replaced only if generated (IP, container id)
  or still an untouched scan result in the inbox.
- `discover(ctx)` (capability `discover`) -> `[{externalId, name, host, kind, state:
  running|stopped, group, presence?}]`; new ones land in the inbox as children.
ctx: `device`, `settings`, `log()`, `sleep(ms)`, `now()`, `secret(settingKey)` ->
`{username, secret, type}`, `util.compareVersions`, `ssh.exec(cmd, {sudo, timeout,
stdin})` -> `{stdout, stderr, code}`, `http.request({method, url, headers, body,
timeout, insecure})` -> `{status, headers, body, json}`, `docker.request(method, path,
body)`. Permissions in the manifest gate ssh/docker/http; HTTP only to the device host
(`httpDevice`) or `httpHosts` (`*.suffix` allowed), redirects included.
`sudo: true` PREFIXES `sudo -n` (no `sh -c`), so a sudoers rule limited to the package
manager works; pass env vars in front of the command (sudoers needs `SETENV`).

- `internal/backup/` - backup targets: `smb` (go-smb2, credential of type password) or
  `local` (absolute path in the container, e.g. `/backups` from the Unraid template).
  Writes go to `<file>.part` then rename. Paths are clamped inside the target.
- `internal/jobs/backup.go` - `backup` job: integration `backup()` returns
  `{name, download: {url, headers}}`; the core checks the URL against the
  integration's allowed hosts, streams it to the target as `<device>/<date>_<name>`,
  keeps the newest `keep` per device and target. Device config `backup`
  {targetId, beforeUpdate, keep}; `beforeUpdate` runs it inside update jobs (a failed
  backup stops the update unless forced). Device config `guards`: [{name, type ssh|http,
  command|url, contains, mode block|warn}] run before every update (ssh: exit 0 = busy;
  http: body contains text = busy).
- `internal/automation/` - scheduler (cron per device: `config.policy` {mode manual|auto|
  scheduled, schedule, scope security|all} and `config.backup.schedule`), pending
  actions (run when the device is next ready), MQTT (`<base>/status`,
  `<base>/device/<slug>/state|updates`, commands on `<base>/device/<slug>/cmd`:
  scan | backup | update | update security). Auto/scheduled updates run as a scan job
  with `thenUpdate`; security scope never selects `os` summary rows.
- API tokens (`hw_...`, Settings, API tokens) authenticate with
  `Authorization: Bearer`; such requests skip the CSRF header check.
  `POST /api/devices/{id}/trigger {action, scope}` is the simple external endpoint.
- `internal/notify/` - channels (discord, ntfy, telegram, gotify, email, webhook; config
  vault-encrypted) and the service that follows server events: new updates /
  security updates (deduplicated in `notify_sent` per component+version), failed or
  blocked jobs, fact warnings (sent once while present), offline after the device's
  `config.notify.offlineMinutes` (+ "back online"). Messages in en/de (global setting).
- Home Assistant: MQTT discovery (setting `haDiscovery`) publishes per device a
  connectivity binary_sensor, an updates sensor and scan/update buttons.
- `internal/monitor/` - uptime monitors (http status/keyword/JSON path/cert expiry, tcp,
  ping, dns, push heartbeat at `/api/push/<token>`, no CSRF); down after 2 failures;
  results kept 30 days. Maintenance windows (global or per device) mute monitor and
  offline notifications. Public status page `/status` (SPA route, data from
  `/api/public/status`: names, state, bars only) for monitors marked public.
- Metrics: capability `metrics(ctx, {smart})` returns {cpu, memPct, memUsedMB,
  memTotalMB, load1, disks[{mount, usedPct, sizeGB}], temps[{name, c}], smart[{dev,
  model, healthy, tempC, hours, reallocated, pending, wearPct, mediaErrors}],
  containers[{name, cpu, memMB}]}. `jobs.MetricsLoop` samples ready devices every 5 min
  (SMART every 12th sample), kept 30 days; warnings disk_full (>=90%), hot (>=80 C),
  smart_failing go to notifications. The Linux snippet is duplicated in linux-apt and
  unraid main.js; keep them in sync.
- SSO: `internal/api/oidc.go` (go-oidc + x/oauth2, PKCE via oauth2.GenerateVerifier,
  state kept in memory 10 min). Settings key `oidc` (client secret vault-encrypted),
  group->role map applied on every login, optional auto-create, local login always
  stays. Redirect URI `/api/auth/oidc/callback` (honours X-Forwarded-Proto/Host).
- Roles may be limited to device groups (`roles.device_groups`, empty = all).
  `Principal.SeesDevice`; enforced in loadDevice (404), device lists, updates, jobs.
- MAC vendors: `internal/oui` reads Wireshark's manuf list, downloaded in the Dockerfile
  to `/usr/local/share/homewarden/manuf` (download failure is tolerated). Device JSON
  gets `vendor` computed from `mac`. MACs come from UniFi discovery (`mac` in
  discover() results) and from `/proc/net/arp` after a network scan (only visible with
  host networking / macvlan).
- `web/src/useEvents.ts` - ONE shared EventSource for the whole app. Never open more:
  each SSE stream holds one of the browser's six HTTP/1.1 connections per host, and the
  device page hung once that ran out.
- `internal/web/` - embeds `dist/` (Vite output; only `.gitkeep` is tracked)
- `web/` - React + TypeScript + Vite. `src/i18n/en.json` + `de.json` must always have
  the same keys. Theme/lang/device-view are per-user prefs (`PUT /api/me/prefs`).
- `Dockerfile` - multi-stage, Go cross-compiled per target arch
- `docker/entrypoint.sh` - PUID/PGID handling
- `unraid/homewarden.xml` - Unraid container template
- `assets/` - icon sources and PNGs
- `.github/workflows/docker.yml` - vet/test, then multi-arch image build and push
